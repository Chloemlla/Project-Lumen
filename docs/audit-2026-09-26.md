# CRooot 错误未进入 lumen-crash 的缺陷清单（2026-09-26）

> 触发：用户报告「修复 lumen-crash 没有捕获到 crooot 的出错」。现场设备为 vivo PD2426（Android 16 / API 36，`ro.build.type=user`、`ro.boot.flash.locked=1`、`ro.boot.verifiedbootstate=green`），只开了 USB 调试、**没有 root**，通过 `C:\adb\adb.exe` 直连调试。
>
> 本清单是修复的唯一依据：每条含唯一编号、文件+行号、缺陷类型、详细症状与根因、建议改法。修复与收尾按编号追溯。
>
> 范围：① `lumen-crash-core`（捕获链路）；② `app/core/security`（CRooot 集成的错误上报）；③ CRooot 侧误判（记录在 §3，不在本轮修复）。

---

## 0. 现场证据（修复前的真实行为）

### 0.1 CRooot 的探针确实在崩，但崩在 fork 出来的子进程里

`adb logcat` 抓到两条 SIGSYS（seccomp trap）tombstone：

```
Fatal signal 31 (SIGSYS), code 1 (SYS_SECCOMP), syscall 142 in tid 32205 (DefaultDispatch), pid 32205 (DefaultDispatch)
Cmdline: com.chloemlla.projectlumen
Cause: seccomp prevented call to disallowed arm64 system call 142
  x0 00000000deadbeef  x1 00000000cafebabe          ← KernelSU reboot-magic supercall 魔数
  #01 libchloemlla-crooot.so
  #03 Java_com_eltavine_duckdetector_features_nativeroot_data_native_NativeRootNativeBridge_nativeCollectSnapshot+56

Fatal signal 31 (SIGSYS) ... syscall 437 in tid 32424 (binder:32237_3), pid 32424 (binder:32237_3)
Cmdline: com.chloemlla.projectlumen:virtualization_probe
Cause: seccomp prevented call to disallowed arm64 system call 437
  x0 ffffffffffffff9c (AT_FDCWD)  x3 0000000000000018 (sizeof(struct open_how))  ← openat2
  #03 Java_com_eltavine_duckdetector_features_virtualization_data_native_VirtualizationNativeBridge_nativeRunSacrificialSyscallPack+44
```

两条 tombstone 都是 `pid == tid`、线程名沿用 fork 它的那个线程（`DefaultDispatch` / `binder:32237_3`）——即 CRooot 的「sacrificial」探针在 `fork()` 出来的**子进程**里发起被 seccomp 拦截的系统调用，子进程被内核杀掉，父进程（app 主进程 / `:virtualization_probe`）靠 `waitpid` 观察到 `SIGSYS` 后继续跑。CRooot 自己也记下了这件事：报告里 `ksuSupercallAttempted: true`、`ksuSupercallBlocked: true`。

### 0.2 这类死亡对两条捕获链路都是不可见的

```
$ adb shell dumpsys activity exit-info com.chloemlla.projectlumen
（共 16 条，全部是 CRooot 自己拉起的隔离探针进程被系统回收）
reason=13 (OTHER KILLS BY SYSTEM) subreason=17 (ISOLATED NOT NEEDED)
  ...TeeGrantDomainGranteeService:duck_grant_domain_*        × 11
  ...VirtualizationIsolatedProbeService / SelinuxContextValidityCarrierService × 5
```

- Java 侧 `Thread.setDefaultUncaughtExceptionHandler`：收不到——死的是 fork 出来的子进程，不是本进程的 Java 线程。
- `ActivityManager.getHistoricalProcessExitReasons()`：收不到——fork 子进程从来不是被 AMS 托管的 app 进程。
- 于是「crooot 的出错」只留在 logcat 里，**没有任何一条进入 lumen-crash**；app 的崩溃页、崩溃上报、breadcrumb 里都没有它的痕迹（实测重启 app 不出现崩溃页，`CrashBreadcrumbs` 无 CRooot 相关条目）。

### 0.3 CRooot 报告的误判（§3 的现场依据）

同一台干净设备上 CRooot 给出 `Root 状态=已 ROOT`、`可疑指标=发现`，于是 `DeviceSecurityGate` 判 `BLOCKED`（`Device security state=BLOCKED`，主进程与两个探针进程都打过这条日志）。逐条核对后确认至少 3 条 HIGH 判据在 stock vivo 上恒真（见 §3）。

## 1. lumen-crash 捕获链路缺陷

### LC-01　`getHistoricalProcessExitReasons` 参数错位：pid 传成了 8，maxNum 传成了 0 —— 整条 prior-exit 捕获路径是死代码

- **编号**：LC-01
- **文件**：`lumen-crash-core/src/main/java/com/chloemlla/lumen/crash/PriorExitCrashCollector.kt:25-29`（`MAX_ENTRIES` 定义在 `:83`）
- **类型**：API 参数语义错误（编译通过、CI 全绿、运行期恒空）
- **现状**：
  ```kotlin
  val exits = activityManager.getHistoricalProcessExitReasons(
      appContext.packageName,
      MAX_ENTRIES,   // ← 这里是 pid，不是条数
      0,             // ← 这里是 maxNum
  )
  ```
- **根因**：官方签名是 `getHistoricalProcessExitReasons(String packageName, int pid, int maxNum)`（API 30 起）。官方 reference 对该方法两个参数的原文是：`pid` —— "A process ID that used to belong to this package but died later; **a value of 0 means to ignore this parameter and return all matching records**"；`maxNum` —— "The maximum number of results to be returned; a value of 0 means to ignore this parameter and return all matching records"。所以这里实际是「只返回 pid == 8 的记录」，而 pid 8 是内核线程，永远不会是本 app 的进程 → `exits` 恒为空 → `if (exits.isEmpty()) return@runCatching null` 恒成立。
- **症状**：`PriorExitCrashCollector.collect()` 永远返回 null，`collectPriorExitReport()` 永远不产出报告。**所有原生崩溃（`REASON_CRASH_NATIVE`）、`REASON_SIGNALED`、ANR、Java 崩溃的「上次退出」捕获全部失效**——这恰好是 CRooot 探针崩溃唯一可能被看见的那条通道。
- **建议改法**：`pid = 0`、`maxNum = MAX_ENTRIES`，并用显式注释锁死参数顺序；同时把 `MAX_ENTRIES` 从 8 提到 32（见 LC-01b）。
- **验证**：改后 `dumpsys activity exit-info` 里出现的 `reason=5 (CRASH_NATIVE)` / `reason=6 (ANR)` 记录才会被读到。

### LC-01b　prior-exit 取数窗口只有 8 条，被 CRooot 自己的隔离探针进程挤满

- **编号**：LC-01b
- **文件**：`lumen-crash-core/src/main/java/com/chloemlla/lumen/crash/PriorExitCrashCollector.kt:83`（`private const val MAX_ENTRIES = 8`）
- **类型**：采样窗口过小 / 噪声淹没信号
- **现状**：`MAX_ENTRIES = 8`；而现场 `dumpsys activity exit-info` 一次扫描就产生十几条 `ISOLATED NOT NEEDED` 记录（CRooot 的 TEE / SELinux / virtualization 隔离探针），全部比真实崩溃更新。
- **根因**：系统侧该历史是环形缓冲（官方 reference 原文："System stores this historical information in a ring buffer and only the most recent records will be returned."），本机实测容量 16。请求 8 条时，只要一次 CRooot 扫描跑过，窗口里就只剩隔离进程回收记录。
- **建议改法**：`MAX_ENTRIES` 提到 32（超过系统容量也无害，等于「全都要」），并加注释说明 CRooot 的隔离探针会churn 这个环。
- **风险/注意**：`capturedReasons` 已经用真实常量 `REASON_CRASH_NATIVE/REASON_SIGNALED/REASON_CRASH/REASON_ANR` 过滤，隔离回收（`REASON_OTHER`）本来就不会被当成崩溃，所以放大窗口不会引入误报。

### LC-02　`processExitReasonName` 常量表整体错位，PRIOR_EXIT 报告的系统原因全被标错

- **编号**：LC-02
- **文件**：`lumen-crash-core/src/main/java/com/chloemlla/lumen/crash/CrashReport.kt:368-386`
- **类型**：常量映射错误（对照官方 reference 核出，§四-10 同族）
- **现状**：代码里的表是 `5->REASON_PERMISSION_CHANGE`、`6->REASON_EXCEPTION`、`10->REASON_ANR`、`13->REASON_CRASH_NATIVE`、`14->REASON_SUSPENDED`、`17->REASON_MEMORY_PRESSURE`、`19->REASON_PACKAGE_UPDATED` …
- **根因**：`ApplicationExitInfo` 的官方常量值是 `REASON_UNKNOWN=0 / EXIT_SELF=1 / SIGNALED=2 / LOW_MEMORY=3 / CRASH=4 / CRASH_NATIVE=5 / ANR=6 / INITIALIZATION_FAILURE=7 / PERMISSION_CHANGE=8 / EXCESSIVE_RESOURCE_USAGE=9 / USER_REQUESTED=10 / USER_STOPPED=11 / DEPENDENCY_DIED=12 / OTHER=13 / FREEZER=14 / PACKAGE_STATE_CHANGE=15 / PACKAGE_UPDATED=16 / MEMORY_LIMITER=17 / ANOMALY=18`。代码从 5 开始整体偏移一位，并且引入了 `REASON_EXCEPTION` / `REASON_DEADLOCK` / `REASON_SUSPENDED` / `REASON_QUIET` / `REASON_MEMORY_PRESSURE` 这些并不存在的名字。
- **症状**：即使 LC-01 修好，报告文字仍然错——CRooot 探针进程的原生崩溃（reason 5）会被写成 `REASON_PERMISSION_CHANGE`，而 CRooot 隔离进程被系统回收（reason 13）会被写成 `REASON_CRASH_NATIVE`，正好把「crooot 的出错」和「crooot 的正常回收」读反。
- **建议改法**：按官方常量值重写整张表，删掉不存在的名字。

### LC-03　`LumenCrash.install()` 在 `Application.attachBaseContext` 里必然抛 NPE，早期窗口没有 reporter

- **编号**：LC-03
- **文件**：`lumen-crash-core/src/main/java/com/chloemlla/lumen/crash/LumenCrash.kt:57-66`（`appContext = application.applicationContext`、`CrashReportStore(application.applicationContext)`）、`:335-337`（`PriorExitCrashCollector(application.applicationContext)`）、`:270-273`（未安装时的 `CrashReportStore(application.applicationContext)`）、`lumen-crash-core/src/main/java/com/chloemlla/lumen/crash/CrashReportStore.kt:27-34`；宿主侧调用点 `app/src/main/java/com/projectlumen/app/ProjectLumenApplication.kt:224-230`
- **类型**：生命周期窗口 / 平台类型空值
- **现状**：宿主在 `attachBaseContext()` 里就装 SDK，现场必然失败：
  ```
  E ProjectLumenApp: LumenCrash install failed in attachBaseContext
  java.lang.NullPointerException: getApplicationContext(...) must not be null
      at com.chloemlla.lumen.crash.LumenCrash.install(...)
      at com.projectlumen.app.ProjectLumenApplication.attachBaseContext(...)
  ```
- **根因**：`Application.attachBaseContext()` 在 `LoadedApk` 记录进程 Application **之前**执行，此刻 `Application.getApplicationContext()`（经 `ContextWrapper` → `ContextImpl` → `mPackageInfo.getApplication()`）仍返回 null。`LumenCrash.install()` 与 `CrashReportStore(context)` 都直接解引用它，Kotlin 对平台类型插入的 `checkNotNullExpressionValue` 抛 NPE。`onCreate()` 里的第二次安装会成功，但 `attachBaseContext → onCreate` 之间的早期启动窗口完全没有 handler。`collectPriorExitReport` 又跑在那个窗口里的后台线程上，`PriorExitCrashCollector(application.applicationContext)` 的同一个 NPE 被 `runCatching` 吞掉 → prior-exit 报告也一并丢失。同模块的 `CrashDeviceId.kt:42` 早就写对了（`applicationContext ?: context`），说明这个坑只在这一处漏了。
- **建议改法**：新增 `Context.crashInstallContext(): Context = applicationContext ?: this`，`install()` 与 `CrashReportStore` 都用它；`Application` 实例本身就是可用的 Context。
- **风险/注意**：`CrashReportStore` 原本刻意捕获 `applicationContext` 以避免持有调用方（可能是 Activity）的引用，改法必须保持这一语义——用一个私有 helper 先解析再闭包捕获，不要直接把入参 `context` 塞进 lambda。

### LC-04　CRooot 的失败从来没有交给崩溃上报：扫描异常只打 log，探针被 seccomp 拦下也没人记

- **编号**：LC-04
- **文件**：`app/src/main/java/com/projectlumen/app/core/security/DeviceSecurityScanner.kt:107-124`（`scan()` 的三个 catch 分支）、`:32`（`class DeviceSecurityScanner(private val context: Context)`）、`app/src/main/java/com/projectlumen/app/core/security/DeviceSecurityGate.kt:46-72`（`startStartupScan` 的 `runCatching` 吞掉）、`:78-82`（`publish` 只打状态）
- **类型**：错误吞噬 / 可观测性缺失
- **现状**：
  ```kotlin
  } catch (e: TimeoutCancellationException) {
      Log.w(TAG, "CRooot scan timed out ...", e); SecurityAssessment.timeout()
  } catch (e: Throwable) {
      Log.e(TAG, "CRooot scan failed.", e); SecurityAssessment.failed(e)
  }
  ```
  超时与异常只进 logcat；`DeviceSecurityGate.startStartupScan` 又用 `runCatching{...}.getOrElse { ... }` 二次吞掉；`publish()` 只 `Log.i(TAG, "Device security state=...")`。CRooot 结果里那些明确的「出错」信号（`nativeRoot.ksuSupercallBlocked`、`stage=FAILED`、各报告的 `errorMessage`）没有任何一条被记录。
- **症状**：现场「crooot 的出错」在 logcat 之外完全不可见——没有非致命报告、没有 breadcrumb，用户交 bugreport 时只有一份 `BLOCKED` 状态。
- **建议改法**：
  1. `DeviceSecurityScanner` 增加可注入的 `failureReporter`，超时/异常时上报 `CroootScanException(phase, message, cause)`；
  2. 新增 `CroootFailureDigest.describe(result)`，把 CRooot 报告里的失败信号压成有界的字符串列表（KernelSU 探针被 seccomp 拦下、`stage`、`errorMessage`、`outcome=SUPPORT` 的探针），**只写标签与计数，不写路径/证书/设备指纹**；
  3. `DeviceSecurityGate.publish()` 把 `state` + digest 记进 `CrashBreadcrumbs`（breadcrumb 随下一次报告一起上报，天然有界 40 条），失败路径再落一条 `recordNonFatal`。

## 3. CRooot 侧误判（本轮只记录，修复需另发 SDK 版本）

现场设备为 stock vivo（未 root），CRooot 却给出 `isRooted = true`，导致 `DeviceSecurityGate` 判 `BLOCKED`。逐条核对 CRooot 源码后确认下列 HIGH 判据在该机型上恒真。**这些改动落在 `CRooot` 仓库，需要重新发布 `crooot-sdk` 并提升 Project-Lumen 的依赖版本才会生效**，故不混进本轮。

### CR-01　`checkBuildFieldCoherence` 对 build id 做严格相等，vivo 的 `_V000L1` 厂商后缀直接触发 HIGH

- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/RootDetector.kt:950-977`（`crossPartitionFingerprintMismatch`）
- **现场取值**：
  - `ro.build.fingerprint` = `vivo/PD2426/PD2426:16/BP2A.250605.031.A3_V000L1/compiler260331112521:user/release-keys`
  - `ro.system.build.fingerprint` = `vivo/PD2426/PD2426:16/BP2A.250605.031.A3/compiler260331112521:user/release-keys`
- **根因**：`hardMismatch` 里 `build.buildId != system.buildId` 是严格相等比较，而 vivo 在 `ro.build.fingerprint` 的 build id 上带厂商后缀 `_V000L1`；`compatibleIncremental()` 已经对 `_` 后缀做了容错，buildId 却没有。
- **症状**：`build_field_coherence`（HIGH）恒命中 → `kkndRoot.isRooted = true`。
- **建议改法**：buildId 比较复用 `compatibleIncremental()` 的容错（或在比较前 `substringBefore('_')`），厂商后缀不得单独构成 HIGH。

### CR-02　`rootPaths` 里的裸 `/debug_ramdisk` 在 stock Android 11+ 上恒存在，`bootLooksTrustedLocked()` 恒为 false

- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/DetectorTrust.kt:110-113`（`hasExplicitRootArtifacts()`）、`HardcodedSignals.kt:79`（`rootPaths` 首项即 `/debug_ramdisk`）
- **现场取值**：`ls -ld /debug_ramdisk` → `drwxr-xr-x 2 root root 27` 且**目录为空**、`/proc/mounts` 里没有它的挂载项。
- **根因**：`/debug_ramdisk` 是 Android 11+ 的 debug ramdisk 挂载点，user build 上常常只剩一个空目录。`hasExplicitRootArtifacts()` 用 `File(path).exists()` 判「有 root 痕迹」，于是任何 stock 设备都返回 true → `bootLooksTrustedLocked()` 恒 false → 所有依赖 `trustedLocked` 的护栏（`hasRootMountSignal` / `isSuspiciousDeletedOrMemfdMap` / `checkWritablePaths` / `checkMountInfoConsistency` / `checkMemfdArtifacts`）全部失效。
- **建议改法**：`hasExplicitRootArtifacts()` 不要把裸 `/debug_ramdisk` 目录本身当作痕迹（`/debug_ramdisk/.magisk`、`/debug_ramdisk/su` 已在 `magiskPaths` / `suPaths` 中，仍会被判到）；或要求该目录非空/确实有挂载。

### CR-03　`rootPackages` 把非 root 的 LSPatch 列进 HIGH 根管理器清单

- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/HardcodedSignals.kt:19`（`rootPackages`）、`RootDetector.kt:178-193`（`checkRootPackages`，HIGH）、`:765-795`（`checkPackageManagerAnomalies`，HIGH）
- **现场取值**：`pm list packages` 与清单求交，命中 `org.lsposed.lspatch`（真实安装在 `/data/app/~~HJYGbLxPzDQphH_l5yGDUg==/org.lsposed.lspatch-.../base.apk`）。
- **根因**：`org.lsposed.lspatch` 同时出现在 `rootPackages`（→ HIGH `root_packages` 与 HIGH `pm_anomalies`）与 `patchedApps`（→ WARNING `patched_apps`）。LSPatch 是**免 root**的 Xposed 方案，把它算作「root 管理器」会让任何装了 LSPatch 的设备被判 root。
- **建议改法**：从 `rootPackages` 移除 `org.lsposed.lspatch`（保留 `patchedApps` 里的 WARNING 归类）；同类需一并复核 `com.tsng.hidemyapplist` / `org.frknkrc44.hma_oss` 等在两表中重复的条目。

### CR-04　`checkADBNetwork` 把 `service.adb.tcp.port=5555` 直接判 HIGH

- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/RootDetector.kt`（`checkADBNetwork`）
- **现场取值**：`getprop service.adb.tcp.port` → `5555`（用户只开了 USB 调试；`/proc/net/tcp` 里并没有 5555 监听）。
- **根因**：判据只看 prop 是否非空，不看端口是否真的在监听；vivo 打开 USB 调试即写入该 prop。
- **症状**：`adb_network`（HIGH）命中 → 开发者设备一律判 root。
- **建议改法**：prop 只作为上下文（WARNING），HIGH 只在 `/proc/net/tcp{,6}` 里真的观察到 5555 `LISTEN` 时给出。
