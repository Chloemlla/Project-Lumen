## LC-01 sample 上报示例里写了跨行的双引号字符串（编译错，本轮唯一硬失败）

- 文件：`lumen-crash-sample/src/main/java/com/chloemlla/lumen/crash/sample/MainActivity.kt:58-59`
- 类型：编译错 / 语法
- 详细错误信息（run `45036910751`，step `Run lumen-crash unit tests`）：
  ```
  > Task :lumen-crash-sample:compileDebugKotlin FAILED
  Syntax error: Expecting '"'.                     line 58
  Unresolved reference 'at'.                       line 59
  Cannot infer type for type parameter 'R'.        line 59
  Function invocation 'run(...)' expected.         line 59
  Unresolved reference 'js'.                       line 59
  Syntax error: Expecting ')'.                     line 59
  Unresolved reference 'claimPendingSlot'.         line 60
  ```

  一条根因（未闭合的双引号）派生 10 条错误，与 §五-5/§五-29 同族：只修最上面那条，其余自动消失。
- 根因：源码写成

- 状态：**已修**，由并行会话在 `920a950`（同一改法）落盘并推送；本清单不再重复改这个文件。
  归因留档：协调者第一次 `awk` 读到的仍是跨行版本，几分钟后同一路径变成已修版本且 mtime 前进 —— 这正是 §三/§五-68
  描述的"同一 clone 被多会话共用"，因此提交前必须重新 `git status` 并按白名单核对暂存区。

## LC-03 非空接收体上的多余安全调用（Kotlin 编译器告警）

- 文件：`lumen-crash-core/src/main/java/com/chloemlla/lumen/crash/LumenCrashConfigBuilder.kt:108`
- 类型：告警 / 空安全表达冗余
- 详细错误信息：
  ```
  Unnecessary safe call on a non-null receiver of type 'CharSequence'.
  ```
- 根因：`PackageManager.getApplicationLabel(ApplicationInfo)` 在 compileSdk 37 的 android.jar 里是 `@NonNull CharSequence`，
  `label?.toString()` 的安全调用是无效表达。
- 改法（已落盘）：把接收体显式声明成可空 —— `val label: CharSequence? = ...getApplicationLabel(appInfo)`，
  于是 `label?.toString()` 不再是无效表达，告警消失，同时保留"框架真返回 null 时不 NPE 在 install 路径上"的兜底。
  直接删 `?.` 也能消警，但会把兜底一起删掉；`resolveAppLabel()` 的返回类型仍是 `String?`（`takeIf` 可空），
  调用点 `appDisplayName?.takeIf{...} ?: resolveAppLabel() ?: packageName` 不受影响。

## LC-04 平台类型上的无效 Elvis（Kotlin 编译器告警，两处）

- 文件：`lumen-crash-core/src/main/java/com/chloemlla/lumen/crash/PriorExitCrashCollector.kt:47,82`
- 类型：告警 / 空安全表达冗余
- 详细错误信息：
  ```
  Elvis operator (?:) always returns the left operand of non-nullable type '(Mutable)List<ApplicationExitInfo!>'.   line 47
  Elvis operator (?:) always returns the left operand of non-nullable type 'String'.                                 line 82
  ```
- 根因：`getHistoricalProcessExitReasons()` 与 `getProcessName()` 的返回被 SDK 注解钉成非空平台类型，
  `?: emptyList()` / `?: ""` 在类型系统里永远走不到右值，于是这两个"防御性兜底"实际是死代码 + 常驻告警。
- 改法（已落盘）：换成仓库既有惯用法 `.orEmpty()`（`CrashDeviceId.kt:97`、`CrashReport.kt:290` 等多处同款）：
  它作用在可空接收体上，对平台类型仍然保留了"真返回 null 时兜底"的语义，同时不再产生告警。
  注意**不要**直接删兜底 —— 那会把 OEM ROM 上偶发的 null 变成 NPE，被外层 `runCatching` 吞掉后
  prior-exit 整批崩溃记录静默丢失（`collect()` 的失败面是"什么都不报"，排查代价远高于一个 orEmpty）。

## LC-05 JVM 测试里对可空 `File?` 直接点调用（Kotlin 编译器告警，两处）

- 文件：`lumen-crash-core/src/test/java/com/chloemlla/lumen/crash/CrashReportPersistenceTest.kt:51,71`
- 类型：告警 / 可空接收体
- 详细错误信息（run `45036910751`）：
  ```
  Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type 'File?'.
  ```
- 根因：JDK 已把 `java.io.File.getParentFile()` 标注为 `@Nullable`（只有根目录返回 null），
  Kotlin 2.x 据此把 `parentFile` 视为 `File?`，`parentFile.mkdirs()` 属于非法直接调用（当前是告警，后续版本会升为错误）。
- 改法（已落盘）：测试里写 `parentFile!!.mkdirs()` —— 临时目录的父目录不可能为空，真为空就是夹具坏了，
  应该立刻抛异常暴露，而不是用 `?.` 静默跳过后在下一行 `writeText` 撞出一个更难读的 `FileNotFoundException`。
