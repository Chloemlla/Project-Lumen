# Project Lumen 后台提醒与悬浮窗链路缺陷清单（2026-09-22）

> 触发：用户报告「软件在后台时无法自动跳出，也没法以直接显示最顶层弹窗的形式提醒用户；给了悬浮窗等诸多权限也没用到正地方，应该直接服务于所有功能」。
>
> 本清单是修复的唯一依据：每条含唯一编号、文件+行号、缺陷类型、详细症状与根因、建议改法。修复与收尾按编号追溯。
>
> 范围：`app/`（Android 客户端）的后台提醒呈现链路 —— 通知、悬浮窗、`LumenToast`、前台服务启动。不涉及后端 / 构建配置。

---

## 0. 现状链路（修复前的真实行为）

后台提醒目前只有两条呈现通道：

| 通道 | 载体 | 谁在用 |
|---|---|---|
| A. 系统通知 | `NotificationCompat` + `AlarmManager` 精确闹钟 | 几乎所有后台提醒 |
| B. 全屏悬浮窗 | `TYPE_APPLICATION_OVERLAY`（`EyeProtectionOverlayService` / `QuarkKeeperAlertService`） | 仅眼保健强制休息、近距离/眨眼严格档、夸克签到截止 |

`SYSTEM_ALERT_WINDOW` 权限在 `AndroidManifest.xml:20` 已声明，`needsOverlayPermission()` / `openOverlaySettings()`（`app/ProjectLumenUiFormatters.kt:433,460`）也已就位并引导用户授权，但通道 B 的调用点只有 5 处，且全部属于眼保健 / QuarkKeeper 两条线：

```
core/services/AlarmReceiver.kt:140          ACTION_BREAK_DUE
core/services/TimerForegroundService.kt:293 RESTING / AWAITING_ACTION
core/services/ReminderActionReceiver.kt:89  用户点「开始休息」
core/proximity/ProximityDetectionService.kt:229 近距离 / 眨眼严格档
openapi/LumenOpenRuntimeController.kt:223   第三方 API 触发
```

**其余全部提醒功能（预提醒、休息结束、番茄钟、用户自建日程提醒、逾期催办、低光照）在后台只有通知，没有任何顶层弹窗通道。**

---

## 1. 缺陷清单

### A-1　后台提醒没有「最顶层弹窗」通道（核心）

- **编号**：A-1
- **文件**：`app/src/main/java/com/projectlumen/app/core/services/NotificationService.kt`
  - `showPreAlert()` 224-233
  - `showBreakDone()` 235-244
  - `showPomodoro()` 246-255
  - `showScheduleReminder()` 257-275
  - `showScheduleOverdue()` 286-296
  - `showLowLightWarning()` 449-468
- **类型**：功能缺陷 / 权限闲置
- **症状**：以上提醒在应用处于后台时，只发一条系统通知。用户正在用别的 App 时，没有任何东西浮到最上层把提醒送到眼前。
- **根因**：这些方法只调用私有的 `show(...)`（`NotificationService.kt:538`），而 `show(...)` 的全部出口都是 `notificationManager.notify(...)`，从未接触 `WindowManager`。顶层弹窗能力只存在于 `EyeProtectionOverlayService`，而它只被眼保健两条线调用（见 §0）。
- **附加证据**：`showScheduleReminder()` 的 `fullScreen = isAlarm`（257-275）是唯一「想弹到最上层」的意图，但它依赖 `setFullScreenIntent`，而：
  - `canUseFullScreenIntents()`（207-210）在 Android 14+ 对非闹钟类应用默认返回 false（`USE_FULL_SCREEN_INTENT` 不再默认授予）；
  - 即使授权，全屏 Intent 也只是「亮屏 + 拉起通知」，不是覆盖在当前 App 之上的窗口。
  于是用户自建的、标记为「闹钟」的日程提醒，在后台实际上什么都看不到。
- **建议改法**：新增统一的顶层弹窗通道（`LumenAlertOverlayService`），由 `NotificationService` 在**进程处于后台且已授权悬浮窗**时同步呈现，覆盖上述全部方法。

### A-2　通知权限被拒时提醒彻底消失，悬浮窗权限在手也不用

- **编号**：A-2
- **文件**：`app/src/main/java/com/projectlumen/app/core/services/NotificationService.kt:548`（`show(...)` 首行 `if (!canPostNotifications()) return`）、`:631-635`（`canPostNotifications()`）、`core/toast/LumenToast.kt:428-429`（fallback 同样先判通知权限）
- **类型**：功能缺陷 / 兜底缺失
- **症状**：Android 13+ 上用户拒绝 `POST_NOTIFICATIONS`（或事后在系统设置里关掉本应用通知）后：
  - `showPreAlert` / `showReminderDue` / `showBreakDone` / `showPomodoro` / `showScheduleReminder` / `showScheduleOverdue` / `showLowLightWarning` 全部在第一行直接 `return`；
  - `LumenToast.showFallbackNotification()` 也直接 return。
  用户此时**仍然持有悬浮窗权限**，系统完全允许本应用把窗口画到最上层——但代码没有任何一条路径去用它。提醒彻底静默。
- **根因**：`show(...)` 把「能不能发通知」当成了「能不能提醒」，两者是独立的权限，没有做降级。
- **建议改法**：`show(...)` 在无法发通知时不再直接 return，改为尝试顶层弹窗；同理 `LumenToast` 的兜底顺序补上悬浮窗分支（`LumenToast.show` 本身已有 `Settings.canDrawOverlays` 分支，但 `showFallbackNotification` 的调用点只在「无悬浮窗权限」时才到达，需一并核对）。

### A-3　后台悬浮提示条点不动，是一块转瞬即逝的死区

- **编号**：A-3
- **文件**：`app/src/main/java/com/projectlumen/app/core/toast/LumenToast.kt:230-262`（`showOverlay`）、`:187-198`（`dismissCurrentImmediately`）
- **类型**：交互缺陷 / 权限未用到位
- **症状**：应用在后台时，`LumenToast.show()` 的前台分支不成立、`Settings.canDrawOverlays` 成立，于是走 `showOverlay()`：在状态栏下方铺一条**全宽**窗口。
  - 窗口 flags 为 `FLAG_NOT_FOCUSABLE or FLAG_NOT_TOUCH_MODAL or FLAG_LAYOUT_IN_SCREEN`（245-247），**没有** `FLAG_NOT_TOUCHABLE`，因此落在该条带内的触摸事件会投递给这个窗口；
  - 但整棵视图树（`createToastView`，295-426）**没有任何 `setOnClickListener`**，用户点它不会有任何反馈——既不开应用，也不关闭；
  - 2.6 秒（`SHORT_DURATION_MILLIS`）或 4.2 秒（`LONG_DURATION_MILLIS`）后自动消失（`scheduleDismiss`，264-268）。
  用户没正眼看着屏幕就完全错过，且这条带子在可见期间是「点上去没反应」的区域。
- **根因**：后台浮层被实现成「会消失的装饰」，而不是「可交互的提醒」。
- **建议改法**：后台浮层补 `setOnClickListener` —— 打开 `MainActivity` 并立即关闭浮层；保留自动消失作为兜底。

### A-4　浮层服务启动失败 / 权限缺失被静默吞掉

- **编号**：A-4
- **文件**：`core/overlay/EyeProtectionOverlayService.kt:214-221`（`show()` 返回 `Boolean`）、全部 5 个调用点（见 §0）均忽略返回值；`core/services/ForegroundServiceController.kt:45-93`（`start()` 同样返回 `Boolean`）
- **类型**：错误处理缺失
- **症状**：`Settings.canDrawOverlays` 为 false、或 Android 12+ 后台启动前台服务被平台拒绝（`ForegroundServiceStartNotAllowedException`，`ForegroundServiceController` 只记日志不抛）时，`show()` 返回 false，调用方当无事发生。眼保健路径因为有并行通知兜底而「看起来还行」，但任何把顶层弹窗当唯一载体的新功能都会静默失效。
- **根因**：返回值无人消费。
- **建议改法**：新的统一弹窗通道把失败结果上报（`recordHandledFailure` 或退回通知），不再静默。

### A-5　常驻 Live Update 状态只活在通知栏，切到别的 App 就看不见

- **编号**：A-5
- **文件**：
  - `core/services/NotificationService.kt:512-525`（`showOngoingStatus`）、`:527-531`（`cancelOngoingStatus`）、`:336-383`（Live Update 构建与签名去重）
  - `core/services/TimerForegroundService.kt:151-155`（1 Hz 驱动，仅在屏幕交互时）
  - `app/ProjectLumenRuntimeFeatureEntry.kt:228-243`（状态刷新入口）
  - 另有 `AlarmReceiver:165`、`BootReceiver:117`、`TimerReconciliationWorker:50`、`ShizukuResilienceWorker:64`、`LumenOpenRuntimeController:242` 五处补发
- **类型**：功能缺陷 / 权限未用到位
- **症状**：计时器运行期间，当前阶段与剩余时间只通过 Live Update 通知呈现。用户切到别的 App 后不看通知栏就完全看不到状态；用户反馈「有时候直接忽略」，即通知栏条目本身不足以让状态被看见。
- **根因**：状态的出口只有一个 —— `notificationManager.notify(NotificationIds.FOREGROUND_TIMER, ...)`。这与 A-1 同源，但 A-1 修的是「事件型」提醒（到点弹一次），「状态型」呈现（运行期间一直在）没有对应通道：`LumenAlertOverlayService` 的卡片 8 秒即自动消失，语义上不能承载常驻状态。
- **附加证据**：
  - Live Update 是**去重发布**的（`shouldPublishLiveUpdate` 比 `signature`，`:1028-1031`），且剩余时间 ≥ 2 分钟时 `useChronometer` 让签名跨秒稳定（`:881` 起的 `timedLiveUpdate`），所以一个阶段内只发布几次 —— 常驻卡片必须支持**原地改文本**，重建窗口会闪。
  - `cancelOngoingStatus()` 有 11 个调用点，覆盖全部 IDLE 转换，常驻卡片的收尾天然有驱动方。
- **建议改法**：`LumenAlertOverlayService` 增加常驻模式（`showStatus` / `dismiss`），与提醒卡片**共用同一个窗口槽位**（提醒到期后把槽位还给常驻状态，而不是关闭服务）；由 `showOngoingStatus` 在去重之前驱动（否则 App 中途切到后台时状态文本没变、卡片永远不出现），由 `cancelOngoingStatus` 收尾。

## 2. 与本次修复的边界（明确不动的部分）

- `EyeProtectionOverlayService` 的全屏强制休息窗**不做可点击化**：它由 `globalOverlayEnabled` 显式开启，语义就是「到点必须停下来休息」，可被点掉会破坏功能本身。
- `QuarkKeeperAlertService` 的截止提醒已经是完整的最顶层弹窗实现（全屏、常驻、三按钮），本次只把它与新通道对齐，不重写。
- 不新增设置项、不改 `globalOverlayEnabled` 的语义（它描述的是「强制休息阻断」，不是「悬浮窗总开关」）；悬浮窗权限本身就是总开关。
- 不重写通知层，不做与本缺陷无关的重构。
- 常驻状态卡片（A-5）**不新增门槛**：它只在 Live Update 已经被驱动的地方被驱动，只是额外要求「进程在后台」+「已授权悬浮窗」这两个它自己的前提。也就是说它和它所镜像的那条通知同生共死，不会出现「关掉通知反而多出一个浮窗」。
- 常驻状态卡片与全屏强制休息窗**允许并存**（两者都是 `TYPE_APPLICATION_OVERLAY`，前者在顶部、后者居中，实测不互相遮挡）。不为这两者引入跨服务的协同状态 —— 那份状态的维护成本高于重复显示一行的代价。
- 常驻状态卡片**不新增交互**：点击行为与 Live Update 通知一致（打开应用并收起卡片），不做暂停/跳过按钮。
- 常驻状态卡片出现的时机取决于 `keepAliveEnabled`：默认开启，`TimerForegroundService` 每秒 tick 一次，切到后台后 1 秒内出现；用户显式关掉保活时，它只在下一次状态变化（预提醒闹钟、阶段切换）时出现。关掉保活本身就是「不要在后台常驻」的明确表达，不为此另加逻辑。
